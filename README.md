# auto-calender-register

Yahoo! JAPANメールから予定を抽出し、Googleカレンダーに登録するためのプロジェクトです。
現在はメールの接続確認・一覧取得・本文取得に加え、**予定候補を選別するdry-run**を実装しています。
Googleカレンダー登録・ICS出力・ローカルOllamaによる文脈判定を実装しています。
Google OAuthとGitHub Secretsは利用者側の設定が必要です。GitHub Actionsの定期実行は初期状態では無効です。

Googleへの登録・OAuth・ICS・GitHub Secretsの手順は [Googleカレンダー連携ガイド](docs/google-calendar.md) を参照してください。

## セットアップ

Node.js 22以上とnpmが必要です。

```sh
npm ci
```

`.env.example` を `.env` にコピーし、次の2項目をローカルで設定してください。
既に `.env` が存在する場合は上書きしないでください。

```dotenv
YAHOO_IMAP_USER=あなたのYahoo!JAPAN_ID
YAHOO_IMAP_PASSWORD=あなたのパスワード
```

認証情報をチャットやGitに貼り付ける必要はありません。`.env` はGitの追跡対象外です。
シェルなどに同名の環境変数がある場合、そちらが優先されます。

Yahoo!メールの「設定」→「IMAP/POP/SMTPアクセス」で、Yahoo! JAPAN公式サービス以外からのアクセスを許可し、IMAPを有効にしてください。
認証にはYahoo! JAPANの公式設定に従ったIDとパスワードが必要です。
接続先は `imap.mail.yahoo.co.jp:993`、TLSを必須としています。
海外版Yahoo Mailのアプリパスワード設定とは異なります。

公式手順: [Yahoo! JAPAN メールソフトで送受信するには](https://support.yahoo-net.jp/PccMail/s/article/H000007321)

## 順番に実行

以下はPowerShellでもそのまま実行できます。

```sh
# 1. 接続確認: メールボックス名・UIDVALIDITY・メール総数
node --import tsx src/cli.ts check

# 2. 最新10件の一覧: UID・件名・送信者・宛先・日時・既読フラグ・サイズ
node --import tsx src/cli.ts list --limit 10

# 3. 一覧に表示されたUIDを指定して本文を取得（123は置き換える）
node --import tsx src/cli.ts show 123

# 4. 最新3件の一覧と本文を順に取得
node --import tsx src/cli.ts inspect --limit 3
```

出力はJSONです。`inspect` は一覧に続けてメールごとのJSONを出力するため、出力全体は単一のJSON文書ではありません。
本文には個人情報が含まれるため、現段階の本文表示コマンドはローカルで実行してください。
IMAPを読み取り専用で開き、既読フラグの変更・送信・削除は行いません。
一覧はIMAPの受信順で新しいものから取得します（メール本文の予定日時やDateヘッダー順ではありません）。

全コマンドで `--mailbox INBOX` を指定できます。省略時は環境変数 `YAHOO_IMAP_MAILBOX`、未設定なら `INBOX` です。
UIDはメールボックス内の識別子です。将来の永続化ではアカウント・メールボックス・UIDVALIDITY・UIDを組み合わせて管理します。

本文取得はMIMEを解析し、日本語件名・本文を復号します。HTMLだけのメールもテキストに変換します。
添付ファイルはファイル名・種別・サイズのみ表示し、保存しません。
取得時は添付を含むメール全体をメモリに読み込むため、1件あたり10MiBまでに制限しています。
必要な場合は `show` / `inspect` に `--max-bytes 20971520` などを指定できます。
大きすぎるメールや取得失敗があれば非ゼロで終了し、後続処理を止めます。
日時出力はUTCのISO形式です。これはメールの送信日時等の表示であり、予定日時の推定はまだ行いません。

## Taskfileで順次実行

`@go-task/cli` を開発依存としてインストールしています。
公式Taskのnpm配布パッケージで、実際のタスク実行エンジンはGo製です。
最新パッケージのインストーラー依存に監査警告があったため、監査が通る `3.45.4` を固定しています。

```sh
# タスク一覧
npm run task

# 接続確認 → 最新10件の一覧 → 最新3件の本文（順次実行）
npm run task mail:review

# 個別実行
npm run task check
npm run task list
npm run task inspect

# 型チェック → テスト
npm run task verify
```

`Taskfile.yml` の `cmds` に定義した順で実行し、途中で失敗したら停止します。
動的な引数を付ける本文確認は上記の `node --import tsx ... show 123` が簡単です。
npm経由なら `npm run cli -- show 123` でも実行できます。
PowerShellでnpmへのオプション転送がうまくいかない場合は `npm.cmd run cli -- list --limit 5` のように `npm.cmd` を使ってください。

## 実装済みの流れと今後の課題

1. 実メールの形式を確認する。
2. ICS添付・予約確認など、構造化された情報や対象を絞ったルールから予定候補を抽出する。
3. 明示されたタイムゾーン・UTCオフセットを解釈し、実行時点より未来の開始日時だけを候補にする。日時や地域が不明な場合は自動登録しない。
4. Googleカレンダーを参照し、ICSのUID・予定キー・正規化した予定情報等で既存予定と照合する。
5. dry-runで登録候補を検証後、明示的な登録コマンドで書き込む。GitHub Actionsのワークフローも用意している。
6. ルールに加えてOllamaを明示指定で利用できる。未確定・矛盾・根拠不足の予定は保留する。

一般的な自由文からの予定判定を、ルールだけで常に正しく行うことはできません。
LLMを使用しても、曖昧な日時やタイムゾーンを確定できるとは限らないため、登録前の検証は必要です。
実メールの少数比較では `qwen3.5:9b` が有望でしたが、全メールでの高精度を保証する段階ではありません。
新着だけを対象にする永続的な差分処理、登録済み予定の変更・取消、hosted runnerでの性能検証は今後の課題です。
GitHub-hosted runnerから手元のOllamaには直接接続できないため、runner上でOllamaとモデルを起動する構成になります。

## 無料運用と実行先

最初はローカル実行が適しています。既存PCで追加のサービス利用料なしに動かせますが、定期実行にはPCの稼働と電力が必要です。

GitHub Actionsは公開リポジトリの標準hosted runnerで無料、非公開リポジトリは契約ごとの無料枠内で運用する必要があります。
将来使う場合は、実測した1回あたりの時間から頻度を決め、超過課金を許可しない設定で運用してください。
今回のメール本文出力を、そのまま公開Actionsのログに流す構成にはしません。
GitHub Actionsのスケジュール実行は指定時刻ぴったりの実行を保証するものではありません。

Cloudflare Workersは今のNode.js CLIをそのまま動かす対象ではなく、採用時にIMAP/TLS対応と無料枠を検証し、実行部分を別途実装します。
ローカルLLMが必要なら、まずローカルまたはGitHub Actionsを候補にします。

外部サービスの将来の料金や無料枠は保証できないため、「永久に完全無料」は保証できません。
有料APIや有料LLMには依存せず、実行先の無料枠内で止められる構成を目指します。

参考: [GitHub Actionsの課金](https://docs.github.com/en/billing/concepts/product-billing/github-actions)、[Actionsの制限](https://docs.github.com/en/actions/reference/limits)、[Taskのインストール](https://taskfile.dev/docs/installation)

## 予定候補のdry-run

2026年10月1日00:00（日本時間）以降に受信したメールを対象にする例です。
受信日はメール本文やDateヘッダーではなくIMAPのINTERNALDATEを使用します。
指定フォルダー内の全対象メールを取得します。未読に限定したり、件数で打ち切ったりしません。

```sh
node --import tsx src/cli.ts dry-run --since 2026-10-01
```

次は実行日の先月初日を自動で選びます。

```sh
npm run task calendar:dry-run
```

出力ファイル（すべて `reports/` 内、Git管理対象外）:

- `dry-run.md`: 候補・未来の日時が記載された要確認予定・その他の要確認メールを確認するレポート。
- `dry-run.json`: 対象外を含む全メールの判定、元メールUID、抽出根拠、理由、候補のGoogle Events形式payload。
- `mail-cache.json`: 取得済みメール本文・ICSのローカルキャッシュ。個人情報を含み、自動削除しません。

本文を再取得せず、現在時刻で再判定する場合:

```sh
node --import tsx src/cli.ts dry-run --since 2026-10-01 --from-cache reports/mail-cache.json
```

キャッシュの受信開始日と `--since` は一致している必要があります。
キャッシュには新着メール・後から届いた変更やキャンセルが反映されません。
実際の登録前は再取得し、カレンダーも再照合する必要があります。
`--output-dir` で保存先を変更できます。クラウドの公開ログ・公開リポジトリには出力しないでください。

判定:

| 値          | 意味                                                                                             |
| ----------- | ------------------------------------------------------------------------------------------------ |
| `candidate` | 予約・参加確定の根拠、未来の開始日時、タイムゾーン、終了日時を確認できた候補。カレンダー照合前。 |
| `review`    | 日時・年・終了時刻・タイムゾーン・参加確定の不足、未対応形式など。自動登録しない。               |
| `pending`   | 予約・参加が未確定。確定通知を受信するまで登録しない。                                           |
| `excluded`  | 過去、キャンセル、広告・一般通知など、現在のルールでの対象外。                                   |
| `duplicate` | 同じ予定の通知、または指定された既存予定スナップショットとの一致。                               |
| `error`     | 本文の取得や解析に失敗。                                                                         |

ルールはICS、日時ラベル付きの日本語・英語本文、CBT試験の科目別日時・試験時間に対応しています。
祝日の曜日表記や、日付と開始時刻が別行のメールも扱います。
ICSの終日・繰り返し・例外予定、自由文、PDFだけに記載された予定は自動登録候補にしません。
メール内のリンクやPDFを開いたり、メールの指示をコマンドとして実行したりはしません。
同じメールに過去と未来の予定が混在する場合は、予定ごとに判定します。

日本語であることやメールの送信時刻だけを根拠に日本時間とは判断しません。
本文の明示タイムゾーン・UTCオフセット・予定の国内会場住所を根拠にします。
終了時刻は時間帯表記または明記された試験時間から計算し、固定の1時間等は補いません。
夏時間の曖昧な時刻や存在しない時刻は保留します。
引用返信の過去本文は原則として抽出しません。

重複通知はICSのUIDや、正規化した予定名・開始日時・場所で照合します。
同じ送信元ドメイン・予約番号の後続キャンセルや未解決の変更があれば、古い候補を停止します。
住所が省略されたリマインダーは、元の予約番号・予定名・現地開始日時の一致から照合します。
送信元が別ドメインの場合や予約番号の表記が違う場合など、全ての重複・キャンセルを検知できるわけではありません。
ルールで拾えないメールもあるため、抽出結果が全予定を網羅する保証はありません。

Googleカレンダーは未接続のため、標準では `calendarDuplicateCheck: "not_connected"` と表示し、
候補の操作を `pending_calendar_duplicate_check` と記録します。既存予定がないと判断したわけではありません。
この `dry-run` コマンドの `calendarWrites` は常に0です。
実カレンダーとの照合・登録は別の `calendar sync` コマンドを使用します。

必要ならGoogle Events形式のJSONスナップショット（予定の配列、または `{ "items": [...] }`）を渡し、
既存予定キー・ICS UID・件名と開始UTC日時の一致を照合できます。
これはGoogle APIからの最新データ取得の代わりではありません。

```sh
node --import tsx src/cli.ts dry-run --since 2026-10-01 --from-cache reports/mail-cache.json --existing-events existing-events.json
```

一部でも取得・解析に失敗した場合は `complete: false`、終了コード2になります。
途中で接続が切れた場合は非ゼロで終了し、途中保存されたキャッシュは `complete: false` のままです。
予定判定の検証は `npm run task verify` で実行できます。

## 転送履歴を見本にした監査とローカルLLM（実験機能）

`Sent` に保存された `Fw:` / `Fwd:` のメールのうち、自分のGmail宛のものを監査用の見本にできます。
Gmailへの接続・転送・Grokbotへの指示は行いません。既存のGrokbotの設定も変更しません。
転送先のGmailが1種類なら自動検出し、複数なら `--recipient` で指定します。

```sh
# 受信キャッシュを取得済みの場合。Sentから転送を読み、ルールで全件監査
node --import tsx src/cli.ts audit-forwards --since 2026-10-01

# メールに再接続せず監査
node --import tsx src/cli.ts audit-forwards --since 2026-10-01 --from-cache reports/sent-forward-cache.json
```

`reports/forward-audit.md` と `forward-audit.json` に、転送元の予定・原本との照合結果・
転送時点と現在時点の判定を出力します。原本の照合は受信キャッシュ内だけが対象です。
元メールが別フォルダーに移動済み・期間外・同じ件名で原本の特定が曖昧な場合は、
「キャッシュ内に一意の原本なし」と表示し、転送本文を検証します。
`>` が付くYahooの転送引用を解除し、元メールの中にある過去の返信引用は除きます。

**転送は「監視したい」という意図の見本であり、確定済みの正解ラベルではありません。**
未確定のリクエスト・キャンセル・変更も転送されるため、その時点の状態を別に判定します。
未転送メールも「不要」という負例にはしません。この監査だけで正解率・再現率は算出できません。
過去の旅程が今の候補に出ないことと、予定の抽出失敗も区別します。

Ollamaの推論を使う場合は、インストール済みのモデル名を明示してください。
今回の少数比較では `qwen3.5:9b` の文脈判定が有望でしたが、全体の高精度を実証したわけではありません。
文面によってモデルが誤判定するため、まだ既定モデルは設定していません。

```sh
# 最初の6件までLLMで検証（ルール監査は全転送が対象）
node --import tsx src/cli.ts audit-forwards --from-cache reports/sent-forward-cache.json --ollama-model qwen3.5:9b --limit 6

# 特定のSent UIDを比較したい場合（123,456はレポートのUIDに置き換え）
node --import tsx src/cli.ts audit-forwards --from-cache reports/sent-forward-cache.json --ollama-model qwen3.5:9b --sample-uids 123,456 --limit 2

# 受信メール全体のうち、候補・要確認・予約や旅程らしい文面を再判定
# 多数の推論が走るため、まず上記の少数監査でモデルを検証してください
node --import tsx src/cli.ts dry-run --since 2026-10-01 --from-cache reports/mail-cache.json --ollama-model qwen3.5:9b
```

API接続先は `http://127.0.0.1:11434` 固定です。メール本文を外部LLMには送信しません。
Ollamaにはローカルにダウンロード済みのGGUFモデルを指定してください。
ローカルモデル一覧・モデル情報を確認し、クラウドモデルと、思考出力を無効にできないモデルは拒否します。
推論は1件ずつ実行し、標準では1件180秒でタイムアウトします。`OLLAMA_TIMEOUT_MS` で1000〜1800000ミリ秒に変更できます。
GitHub Actionsの例ではCPU推論向けに600秒とし、ストリーミングで応答を読み取ります。CLI自身はモデルを自動ダウンロードしません。
転送監査の推論結果はモデル名・入力・プロンプト版ごとに `ollama-cache.json` に保存します。
受信全体のdry-runでの推論は現時点では毎回実行します。

LLMは本人の予定／営業／未確定／取消を区別し、根拠の原文と現地日時・タイムゾーンをJSONにします。
その後にコードで、引用が本文にあるか、引用した年月日・時刻との一致、タイムゾーンの根拠、
夏時間、未来日時、終了日時を検証します。国・都市からのタイムゾーン判定は検証対象の地域に限ります。
モデルがIANA名だけを捏造引用した場合や、確定根拠が不足する場合は登録案にしません。
離れた行を結合した引用は、モデルが挙げた行のうち本文に連続して実在する根拠だけに絞ります。

新しい判定 `pending` は「未確定・確定通知待ち」です。抽選待ちや予約リクエストを登録しません。
後から確定メールを受信したらそのメールを再評価します。予約ルールとLLMが食い違う場合も保留します。
LLMも確定と判断して開始日時が一致する場合は、モデルが終了日時を取りこぼしても既存ルールで検証済みの終了を使用します。
モデルの抽出・検証に失敗した場合は `error` とし、自動登録しません。

モデル名が同じでも更新後は挙動が変わる可能性があります。監査キャッシュはモデル名ベースなので、
モデルを更新した場合は別の `--output-dir` を指定して再評価してください。
参考: [Ollamaの構造化出力](https://docs.ollama.com/capabilities/structured-outputs)

## コードの整形

Prettierを開発依存としてバージョン固定で導入しています。

```sh
# ファイルを整形
npm run format

# 変更せず、整形済みか確認
npm run format:check
```

Taskfile経由では `npm run task format` / `npm run task format:check` でも実行できます。
`npm run task verify` は整形チェック・型チェック・テストを順番に実行します。
設定は `.prettierrc.json`、対象外は `.prettierignore` に記載しています。
メール本文を含む `reports/`、環境変数ファイル、生成物、ロックファイルは整形対象外です。
